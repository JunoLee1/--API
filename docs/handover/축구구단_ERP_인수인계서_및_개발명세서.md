# [업무 인수인계서] 축구 구단 내부 ERP 개발 및 운영 (의료 통계/의료비 모듈)

본 문서는 축구 구단 내부 ERP(Enterprise Resource Planning) 시스템의 **'의료 통계 및 의료비 관리 모듈'**과 관련하여, 후임 개발자 및 운영 담당자가 업무를 원활하게 이어받을 수 있도록 시스템 아키텍처, 데이터 구조, 비즈니스 로직 및 실무 운영 프로세스를 정리한 인수인계서입니다.

---

## 1. 업무 개요 및 목적
* **업무명**: 축구 구단 내부 ERP - 선수 부상 관리, 의료비 정산 및 보험 청구 시스템 개발·운영
* **목적**: 
  * 선수의 부상 이력 및 재활 상태를 실시간 추적하여 팀 가동률을 극대화함.
  * 병원 진료비, 수술비, 재활비 등 구단 지출 의료비의 투명한 정산 및 보험 환급 흐름을 자동화하여 재무 리스크를 최소화함.
* **주요 협업 부서**: 의무 팀(메디컬 스태프), 프런트 운영 팀, 재무/회계 팀

## 2. 시스템 아키텍처 및 데이터베이스 구조

### 2.1 데이터 모델 연동 방식
의료 모듈은 구단의 기본 자산인 **선수 마스터 테이블(`Player`)**을 중심으로 1:N 관계 체인으로 엮여 있습니다.
* 선수가 부상을 당하면 `Injury_Log`에 고유한 `injury_id`가 생성됩니다.
* 해당 부상 건으로 발생하는 모든 병원 영수증 및 지출은 `Medical_Expense` 테이블에 `injury_id`를 참조(FK)하여 N건 쌓이게 됩니다.
* 보험금 환급 내역 또한 동일한 `injury_id`를 기준으로 매칭됩니다.

### 2.2 핵심 DB 스키마 DDL (요약)
후임자가 로컬 환경 구축 및 쿼리 테스트 시 참고할 마스터 테이블 구조입니다.

```sql
-- 1) 선수 마스터
CREATE TABLE Player (
    player_id VARCHAR(20) PRIMARY KEY,
    name VARCHAR(50) NOT NULL,
    position VARCHAR(10),
    status VARCHAR(20) DEFAULT 'Active' -- Active, Injured, Loan, Transferred
);

-- 2) 부상 및 진료 기록
CREATE TABLE Injury_Log (
    injury_id VARCHAR(20) PRIMARY KEY,
    player_id VARCHAR(20) NOT NULL,
    occurrence_date DATE NOT NULL,
    body_part VARCHAR(30) NOT NULL,
    injury_type VARCHAR(50) NOT NULL,
    surgery_yn CHAR(1) DEFAULT 'N',
    recurrence_yn CHAR(1) DEFAULT 'N',
    return_date DATE,
    current_status VARCHAR(20) NOT NULL, -- 치료중, 재활중, 복귀완료
    FOREIGN KEY (player_id) REFERENCES Player(player_id)
);

-- 3) 의료비 지출 내역
CREATE TABLE Medical_Expense (
    expense_id SERIAL PRIMARY KEY,
    injury_id VARCHAR(20) NOT NULL,
    receipt_date DATE NOT NULL,
    cost_category VARCHAR(30) NOT NULL, -- 외래진료비, 검사비, 수술비, 재활비, 약제비
    total_amount INT NOT NULL,
    payer_type VARCHAR(20) NOT NULL,    -- 구단, 협회, 개인
    FOREIGN KEY (injury_id) REFERENCES Injury_Log(injury_id)
);
```

## 3. 핵심 비즈니스 로직 및 상태 변경 프로세스

의료 모듈 개발 시 가장 유의해야 할 점은 **의무 팀의 입력 상태**와 **재무 팀의 보험 청구 프로세스**가 트리거로 연결되어 있다는 점입니다.

### 3.1 단계별 로직 흐름
1. **[부상 발생] 상태 (`치료중`)**
   * 의무 팀이 ERP에 부상 정보를 입력하면, 시스템은 선수의 기본 정보(연봉 수준 등)를 파악하여 '프로축구협회 저연봉 선수 수술비 지원 대상' 등 지원 제도 플래그를 백엔드에서 체크합니다.
2. **[비용 발생 및 영수증 등록]**
   * 영수증이 등록될 때마다 `payer_type`이 '구단'인 경우, `Insurance_Claim` 테이블에 자동으로 **[청구 대기]** 레코드가 생성되도록 트리거가 설정되어 있습니다.
3. **[재활 단계] 상태 전환**
   * 선수가 수술을 마치고 `current_status`가 **`재활중`**으로 변경되면, 프런트 담당자 화면에 '보험 청구 필수 서류(진단서, MRI 등) 업로드 알림'이 발송됩니다.
4. **[복귀 완료 및 정산 종결]**
   * 선수가 훈련에 복귀하고 보험금 입금이 확인되면 상태를 **`지급완료`**로 변경합니다. 이때 `구단 순부담액(총 비용 - 보험 환급액)`이 실시간 계산되어 대시보드 KPI에 반영됩니다.

## 4. 부서별 권한 체계 및 결재 프로세스 (Admin-Finance 겸임 구조)

실무 운영 효율성을 극대화하기 위해 **Admin(최고 관리자)이 Finance(재무/회계) 역할을 겸임**하는 구조로 설계되어 있습니다. 이에 따라 결재선과 권한 구조를 간소화하여 빠른 의사결정이 가능하도록 구현했습니다.

### 4.1 부서별 역할 및 권한 정의 (RBAC)

Admin을 제외한 현장 실무 부서인 **의무 팀**과 **운영 팀**에는 각각 팀장 역할을 두어 민감 데이터 접근 제어 및 1차 검토 책임을 명확히 하고, **재무 승인은 Admin이 직접 수행**합니다.

* **의무 팀 (Medical Team)**
  * **일반 팀원 (Staff)**: 일일 치료 기록 입력, 담당 선수 재활 일지 작성 (기본 CRUD 권한).
  * **의무 팀장 (Leader)**: 진단명 최종 확정, 복귀 예정일 및 상태 변경(`치료중` ➔ `재활중` ➔ `복귀완료`) 승인 및 확정 권한.
* **프런트 / 운영 팀 (Operations Team)**
  * **일반 팀원 (Staff)**: 진료비 영수증 등록, 보험 청구 필요 서류 취합 및 상신.
  * **운영 팀장 (Leader)**: 의무 팀 상태값 대조 검토, 구단 공식 보험 청구 건 1차 결재 및 Admin 상신.
* **최고 관리자 / 재무 겸임 (Admin / Finance)**
  * **Admin**: 시스템 통합 관리 및 사용자 권한 변경 기능 + **[고액 의료비 선지급 승인 및 보험 미수금 최종 정산/종결 권한]** 겸임.

### 4.2 단축 결재 프로세스 (Workflow)

Finance 전용 팀장 단계를 생략하고 Admin 승인 단계로 즉시 연결되는 **단축 3단계 결재선**을 적용하였습니다.

```
[운영 팀원] 영수증 및 청구 서류 등록/상신
      ▼
[운영 팀장] 서류 검토 및 1차 결재 승인 (Admin 상신)
      ▼
[Admin (Finance 겸임)] 최종 지출 승인 및 장부 정산 확정 (입금 확인 후 종결)
```

### 4.3 개발 및 설계 유의사항 (후임 개발자 참고)
1. **권한 매핑 방식 (Permission-Based)**: 
   * 소스코드 내부에서 `if (user.role === 'ADMIN')`과 같이 단일 역할로만 재무 권한을 제어하지 마십시오.
   * `SYSTEM_MANAGE`(시스템 설정) 권한과 `FINANCE_APPROVE`(재무 승인) 권한을 분리하여 설계해야 합니다. (추후 Finance 전용 계정 분리 시 코드 수정 없이 권한 매핑만 변경하기 위함)
2. **감사 로그 (Audit Log) 필수 기록**:
   * 재무 승인을 Admin 계정군(`admin_juno` 등)에서 처리하더라도, 어떤 구체적 세션 ID가 최종 승인 API를 호출했는지 감사 로그 테이블(`Audit_Log`)에 반드시 기록을 남겨야 합니다.

## 5. 실무 운영 및 모니터터링 (KPI / SQL)

### 4.1 대시보드 주요 관리 지표 (KPI)
운영계 대시보드 화면 배치 및 배치(Batch) 작업 점검 시 아래 지표들의 계산 수식을 확인해야 합니다.
* **팀 가동률**: 전체 등록 선수 대비 출전 가능 선수의 일자별 비율
* **평균 복귀 소요 기간(ATR)**: 부상 부위별/종류별 복귀 평균 일수
* **보험 회수율**: `(총 보험금 수령액 / 총 발생 의료비) * 100`

### 4.2 주기적 데이터 검증용 SQL 쿼리
정기 정산 시나 데이터 정합성 체크 시 아래 쿼리를 활용하여 '부상 부위별 통계' 및 '구단 실부담 순위'를 모니터링합니다.

```sql
-- 부상 부위별 발생 비용 및 평균 결장일수 추출
SELECT 
    i.body_part,
    COUNT(i.injury_id) AS injury_count,
    AVG(DATEDIFF(day, i.occurrence_date, ISNULL(i.return_date, GETDATE()))) AS avg_days_lost,
    SUM(e.total_amount) AS total_cost
FROM Injury_Log i
LEFT JOIN Medical_Expense e ON i.injury_id = e.injury_id
GROUP BY i.body_part;
```

## 6. 감독 대시보드 및 전술 섹션의 이원화 설계 (전술판 구현 가이드)

본 시스템은 축구단 운영의 직관성과 전술적 전문성을 모두 충족하기 위해 **'감독 대시보드'와 '상세 전술 섹션'의 전술판 렌더링 방식을 목적에 맞게 이원화**하여 설계했습니다.

### 6.1 화면별 전술판 설계 컨셉 및 목적

| 화면 구분 | 적용 전술판 형태 | 핵심 목적 | 시각적 특징 및 주요 기능 |
| :--- | :--- | :--- | :--- |
| **감독 대시보드 (Dashboard)** | **일반 포메이션 판** (Standard Pitch) | 신속한 현황 파악 (Overview) | - 익숙하고 심플한 녹색 잔디 배경<br>- 당일 선발 포메이션(4-3-3, 3-4-3 등) 및 라인업 요약<br>- 부상자 아이콘 표시 및 교체 명단 직관적 확인 |
| **상세 전술 섹션 (Tactical Area)**| **스페인식 전술판** (Pizarra Táctica) | 디테일한 전술 수립 (Analysis) | - 세로 5개 채널(Pasillos) 및 하프스페이스 가이드 점선 구현<br>- 포지셔널 플레이(Juego de Posición) 조정을 위한 경량 드래그 기능<br>- 삼각형/다이아몬드 패스 라인 구조 확인 |

### 6.2 프론트엔드(CSR) 데이터 동기화 구조

두 전술판은 시각적 레이어(SVG 디자인)만 다를 뿐, **동일한 선수 상태 데이터 모델을 공유**하도록 설계하여 실무 편의성과 개발 효율성을 극대화합니다.

```
[감독 대시보드]에서 라인업/포메이션 확정
      ▼ (선수 ID, 포지션 데이터 백엔드 저장)
[상세 전술 섹션] 진입 시 해당 라인업 데이터 자동 로드
      ▼ (동일한 선수 자석 토큰이 스페인 전술판에 자동 배치됨)
[스페인 전술판] 세로 5분할 가이드라인 위에서 드래그하며 디테일한 전술 훈련 세션 설계
```

### 6.3 개발 및 컴포넌트 설계 가이드 (후임자 참고)
1. **SVG ViewBox 재사용**: 
   * 일반 포메이션 판과 스페인 전술판 모두 `viewBox="0 0 1000 600"` 규격을 동일하게 공유하도록 개발하십시오. 이를 통해 선수 토큰의 `(x, y)` 좌표 데이터가 두 화면 간에 왜곡 없이 1:1로 매핑됩니다.
2. **뷰 스위칭 (View Switching) 구현**:
   * 전술 섹션 내에 `Show Pasillos (5분할 가이드 켜기/끄기)` 토글 버튼을 배치하여, 하나의 컴포넌트 내에서 조건부 렌더링(`{showPasillos && <line ... />}`)을 통해 두 가지 뷰를 부드럽게 오갈 수 있도록 구현하는 것이 유지보수에 유리합니다.

## 7. 경기/분석 섹션 - 리그/팀 순위 조회 권한 설계

경기력 분석 및 구단 운영의 투명성을 높이기 위해, **경기/분석 섹션의 '팀 순위(리그 테이블)' 정보는 Admin뿐만 아니라 구단 내부의 모든 직원(의무, 운영 등)이 자유롭게 조회할 수 있도록** 권한 범위를 넓혀 설계했습니다.

### 7.1 권한 매핑 및 접근 정책

보안과 프라이버시가 엄격히 제한되는 의료 데이터나 재무 결재와 달리, 리그 순위 및 팀 성적 데이터는 구성원 전체가 상시 공유하며 동기부여를 얻고 경기력 분석의 기초 자료로 활용해야 하는 공공 데이터(Public-in-Club)의 성격을 가집니다.

* **접근 정책**: 
  * `VIEW_TEAM_RANKING`(팀 순위 조회) 권한은 구단 내부 모든 역할군(`Staff`, `Leader`, `Admin`)에 기본 활성화(True)됩니다.
  * 외부 비인증 사용자나 에이전트 등 외부 계정은 차단됩니다.

```sql
-- 예시: 권한 제어(ACL) 검증 로직 컨셉
-- 모든 구단 내부 사용자는 부서에 상관없이 팀 순위 API(GET /api/analysis/rankings) 호출 권한을 가짐
SELECT CASE 
    WHEN u.active_yn = 'Y' AND u.department IN ('Medical', 'Operations', 'Finance', 'Coaching') THEN 'ALLOW'
    ELSE 'DENY'
END AS access_status
FROM ERP_User u
WHERE u.user_id = :current_user_id;
```

### 7.2 화면 구성 및 UI 반영 가이드
1. **네비게이션 바 노출**:
   * 의무 팀이나 운영 팀 계정으로 로그인하더라도 LNB(Left Navigation Bar)의 `경기/분석 ➔ 팀 순위` 메뉴가 숨김 처리되지 않고 노출되도록 구현합니다.
2. **독립적인 API 엔드포인트 설계**:
   * 팀 순위 렌더링을 위한 API는 민감한 선수 세부 분석 지표 API와 결합하지 않고, `GET /api/analysis/rankings`로 독립적으로 쪼개어 설계하십시오. 
   * 이렇게 하면 타 부서 직원이 순위를 조회할 때 다른 민감 정보(예: 선수 개인 평점 기록 등)에 접근하는 보안 사고를 미연에 방지할 수 있습니다.

## 8. 경기/분석 섹션 - 팀 단위 분석 데이터 및 선수 통계의 균형 설계 (개선 과제)

현재 시스템의 경기/분석 섹션에서 **팀 경기(Team Match) 분석임에도 불구하고 개인 선수의 수치(스탯)만 출력되는 이슈**가 식별되었습니다. 팀의 전술적 흐름과 협동적 경기력을 정확히 진단할 수 있도록, **'팀 전체 통합 데이터'와 '개인 통계'를 상호 보완적으로 렌더링하도록 개선하는 설계 사양**을 추가합니다.

### 8.1 문제 정의 및 개선 방향

* **현재 문제**: 팀 경기 전체의 전술 성과를 평가해야 하는 화면에서 개인 선수 스탯(패스 횟수, 러닝 거리 등)만 개별적으로 나열되어, 전체 팀의 유기적인 빌드업 구조나 공수 밸런스를 파악하기 어려움.
* **개선 방향**:
  1. 경기 분석 첫 화면에 **팀 전체 누적/평균 데이터(Team Metric)**를 최우선으로 배치.
  2. 그 하단 또는 우측 탭에 팀원들의 **개인 기여도(Player Metric) 및 세부 데이터**를 매핑하여 '팀 성적 ➔ 개인 지표'로 이어지는 탑다운(Top-down) 분석 흐름 구축.

### 8.2 데이터 모델 확장 및 렌더링 설계

#### 1) 팀 경기 분석 테이블 구조 확장 (예시)
개 개별 선수의 데이터를 집계하여 매번 실시간 연산하는 성능 낭비를 막기 위해, 경기 종료 후 **팀 단위의 경기 통계를 별도로 저장하는 집계 테이블(`Team_Match_Analysis`)**을 두거나 뷰(View)를 설계합니다.

```sql
CREATE TABLE Team_Match_Analysis (
    match_id VARCHAR(20) PRIMARY KEY,        -- 경기 고유 ID
    possession_rate INT NOT NULL,            -- 팀 전체 점유율 (%)
    total_passes INT NOT NULL,               -- 팀 전체 패스 시도 횟수
    successful_passes INT NOT NULL,          -- 팀 전체 패스 성공 횟수
    pass_accuracy AS (successful_passes * 100 / total_passes), -- 패스 성공률 (자동 계산)
    total_distance_run DECIMAL(5,2),         -- 팀 전체 활동량 총합 (km)
    shooting_count INT NOT NULL,             -- 팀 전체 슈팅 수
    shooting_on_target INT NOT NULL          -- 팀 전체 유효 슈팅 수
);
```

#### 2) 화면 UI 레이아웃 변경 명세
* **상단 (Team Dashboard Area)**:
  * 팀 전체 점유율, 총 슈팅 수, 패스 성공률, 활동량 총합 등 **팀 종합 스탯**을 스페인 전술판 배경의 미니 맵이나 인포그래픽 카드로 시각화.
* **하단 (Individual Contribution Area)**:
  * 팀 전체 데이터 아래에 **"선수별 세부 기여도"** 목록을 배치.
  * 예: "팀의 총 패스 100회 중 A 선수가 25회 관여(25%)"와 같은 방식으로 팀 데이터와 개인 데이터를 직관적으로 매칭.

## 9. 인수인계 사항 및 향후 과제
* **엑셀 데이터 마이그레이션**: 현재 기존 수기 관리되던 엑셀 데이터 파일(선수별 부상 기록 및 영수증 내역)의 구조가 본 문서 2번의 DB 스키마 구조와 1:1 매칭되도록 데이터 파이프라인 정제 스크립트(`migration_script.js`) 작성이 완료되어 있습니다. 시스템 오픈 시 해당 스크립트를 가동하여 초기 데이터를 적재해야 합니다.
* **외부 API 연동 확장 (예정)**: 향후 국민건강보험 일괄 조회 또는 협회 ERP 시스템과의 API 연동을 통해 수술비 청구 프로세스를 간소화하는 고도화 작업이 계획되어 있습니다.
